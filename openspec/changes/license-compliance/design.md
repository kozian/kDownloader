# Design

## Context

Tools are described in `tools/manifest.json` (URL, SHA-256, kind). The Xcode build
phase `embed-tools.sh` runs `fetch-tools.sh`, which downloads, verifies and caches
them in `.build/tools`, then copies them into the bundle: yt-dlp to
`Contents/Resources/yt-dlp`, ffmpeg/ffprobe/Deno to `Contents/Helpers`.
`update-tools.sh` rewrites the release manifest and derives the Debug manifest
(`manifest-update-test.json`) from it with an older yt-dlp.

What each source ships today:

- **FFmpeg source tarball:** `COPYING.LGPLv2.1` and `LICENSE.md`. The
  configure options are in `scripts/build-ffmpeg.sh` and are reported by
  `ffmpeg -buildconf`.
- **Deno release zip:** the binary only. `LICENSE.md` is in the repository at
  the release tag.
- **`yt-dlp_macos.zip`:** `_internal/THIRD_PARTY_LICENSES.txt` and the
  `dist-info` licenses. yt-dlp's own `LICENSE` (Unlicense) is in the repository
  at the release tag.

## Goals / Non-Goals

**Goals:**
- Every built app (Debug, Release, update test) carries the notices of exactly
  the versions it bundles, with no manual step.
- License texts come from the same upstream as the tools and are pinned like
  them.

**Non-Goals:**
- Generating notices for the dependencies inside Deno (V8, Rust crates):
  Deno publishes no aggregated notice (see Risks).
- Notices for a yt-dlp update installed by the app: the user downloads it from
  GitHub themselves, and it carries its own `THIRD_PARTY_LICENSES.txt`.
- Legal review; replacing the app icon (backlog).

## Decisions

### One folder per component, not one combined THIRD_PARTY_LICENSES.txt
`Contents/Resources/Licenses/{kDownloader,FFmpeg,Deno,yt-dlp}/`, with the upstream
files kept as they are.

- Each folder is copied, verified and replaced as a unit when its tool changes.
- The release check is a list of paths.

A single concatenated file, like yt-dlp's, is also legally fine: the licenses
require the text to be included, not a format. Its downsides here:
- it must be regenerated by a script on every tool update, and a hand-edited
  section can go stale without anyone noticing;
- yt-dlp's 4,700-line aggregate would be nested inside it;
- checking that one component's text is present means parsing the file.

### Manifest entries for license files
Each tool gets a `licenses` array of `{ "url", "sha256", "as" }` for files
downloaded from the upstream repository at the release tag, or
`{ "fromArchive": "<path>", "as" }` for files taken from the verified tool
archive. Examples:

```json
"licenses": [
  { "url": "https://raw.githubusercontent.com/denoland/deno/v2.9.8/LICENSE.md",
    "sha256": "…", "as": "LICENSE.md" }
]
```

FFmpeg uses `fromArchive` for `ffmpeg-<v>/COPYING.LGPLv2.1` and
`ffmpeg-<v>/LICENSE.md`. yt-dlp uses a `url` entry for `LICENSE` and a
`fromArchive` entry for `_internal/THIRD_PARTY_LICENSES.txt`.

- `fetch-tools.sh` downloads, verifies and caches the files with the same
  `fetch` function and writes them to `.build/tools/licenses/<Component>/`. A
  mismatch fails the build, naming the file.
- The licenses folder is rebuilt on every run, from cached files, instead of
  being tracked by the tool stamps. It is a few small files, and a stale license
  can never survive a manifest change. Archive paths may contain `{version}`
  (FFmpeg: `ffmpeg-{version}/COPYING.LGPLv2.1`), so a version bump needs no
  path edit.

*Alternative:* commit the license texts to the repository. That is simpler to
build, but the texts would drift from the bundled versions unless someone
remembers to update them, which defeats the per-version requirement.

### update-tools.sh pins licenses with versions
- For yt-dlp and Deno it rewrites the `url` to the new tag and sets the SHA-256
  of the downloaded file. Since there is no published checksum for these files,
  they are pinned on first download. This is acceptable for plain text, which
  the build verifies from then on.
- `fromArchive` entries need no update, because the archive itself is verified.
- The Debug manifest is derived as today. The yt-dlp object is replaced as a
  whole, so its licenses follow the older version.

### FFmpeg build notice generated at build time
`embed-tools.sh` writes `Licenses/FFmpeg/BUILD.txt` with:
- the version;
- the source URL and SHA-256 from the manifest;
- the output of the bundled `ffmpeg -hide_banner -buildconf`, so the configure
  options are those of the actual binary;
- the sentence "The source tarball is published next to each kDownloader
  release as ffmpeg-<v>.tar.xz".

It also copies `scripts/build-ffmpeg.sh`, the build script required by LGPL
§0/§6. The kDownloader `LICENSE` is copied from the repository root.

### Release: license check and FFmpeg source
- `release.sh` gets `check_licenses`, a list of the expected files, each of which
  must be non-empty. It runs in both releases and dry runs.
- On a real release, after the zip, it copies the verified tarball from
  `.build/tools-cache` to `dist/ffmpeg-<v>.tar.xz` if no file of that name exists,
  and writes `.sha256`. If the file exists with a different checksum, the release
  stops.
- One tarball serves every release that bundles the same FFmpeg version.

### About window
Under the app name and version, a "Bundled dependencies" heading with a grid of
yt-dlp (with its "updated" mark), FFmpeg and Deno and their versions. The app's
own version is not repeated as a row.

Below it, a "Show Licenses in Finder" link opens the `Licenses` folder with
`NSWorkspace.open`. There are no per-license links: the texts are files the
user reads in Finder or Quick Look, so the app needs no viewer of its own. The
FFmpeg source URL is in `Licenses/FFmpeg/BUILD.txt`. All strings are added in ru
and en.

## Risks / Trade-offs

- **[Risk]** Deno's binary embeds V8 (BSD-3) and many Rust crates
  (MIT/Apache-2.0) whose notices Deno does not publish together.
  → Ship Deno's `LICENSE.md` and record the gap in the README. A complete notice
  would need `cargo about` over Deno's lockfile per release; it is noted as
  a backlog idea if ever needed.
- **[Risk]** `raw.githubusercontent.com` is unavailable during a build.
  → The license files are cached like the tools. The first build needs network
  anyway.
- **[Risk]** A future yt-dlp build stops shipping `THIRD_PARTY_LICENSES.txt`.
  → The `fromArchive` copy fails the build, so the change is noticed when the
  tools are updated, not after release.
- **[Trade-off]** The FFmpeg tarball (~11 MB) must be handed out with the zip.
  The README "Installing" section says so: share both files, or link to the
  folder where they are.

## Migration Plan

- No user data changes.
- The first build after the change downloads the license files.
- The next release, 0.2.2, is the first compliant one. Releases 0.1.0
  to 0.2.1 already given out are not rebuilt; their FFmpeg version is the same
  (9.0.2), so the published tarball also covers them.
